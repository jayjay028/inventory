1. System Overview

Purpose and Scope

The MaraCoder Inventory+POS is a comprehensive enterprise-grade application designed for small and medium enterprises (SMEs) in the Philippines. It provides end-to-end inventory management, point-of-sale operations, financial reporting, and compliance with Philippine regulatory requirements.

The system covers the complete business cycle from procurement (stock-in) through sales (POS) to reporting and auditing, all within a single integrated platform.

Target Users

  • Small and medium retail businesses in the Philippines
  • Convenience stores, sari-sari stores, and mini-marts
  • Hardware stores and supply shops
  • Food and beverage retail outlets
  • Any Philippine SME requiring inventory tracking and POS capabilities

Key Features

  • Multi-Store Support — Per-store stock, sales, and shifts; per-user store access with backend enforcement; per-store document numbering; shared global master data
  • Dynamic Roles & Permissions — Admin-managed roles holding a permission bitmask; users inherit permissions from their assigned role; reserved system ADMIN role; role management gated by MANAGE_USERS
  • Inventory Management — Item catalog, categories, stock-in/out/adjust, stock level monitoring, reorder alerts
  • Point of Sale — Fast item lookup, barcode support, multiple payment methods, receipt generation, shift management
  • Customer & Supplier Management — Contact database, transaction history, balance tracking
  • Financial Reporting — Sales reports, inventory valuation, profit analysis, daily/weekly/monthly summaries
  • User Management — Role-based access, 25 granular permissions, audit trail
  • JasperReports Integration — 19 professional PDF report templates
  • Philippine Compliance — BIR-compliant VAT computation, official receipt numbering, senior/PWD discounts

Frontend theme: The UI supports both light and dark themes, driven by CSS custom properties (e.g. --color-primary, --brand-gradient, surface and text colors defined in app.css) whose values switch based on a data-theme attribute on the root <html> element. The brand identity is the MaraCoder blue-to-teal accent (primary #2563eb, cyan #06b6d4, teal #14b8a6) matching the MaraCoder logo, with the dark theme using dark slate surfaces (#0f172a / #111c33) and the light theme using light surfaces. Navigation is SPA-based (Vue Router): the top-bar brand links to the user's landing page, and the sidebar auto-expands the group containing the active route.

Security Architecture

  • Authentication: Stateless JWT (access + refresh token pair)
  • Password Storage: bcrypt with cost factor 10
  • Authorization: Bitwise permission model (25 permissions encoded in a single integer)
  • Permission Check: Custom @RequiresPermission annotation with AOP aspect
  • Token Invalidation: In-memory deny list cleared on server restart; refresh tokens stored in DB

Multi-Store Architecture

The system supports multiple physical stores/branches operating against a single deployment. Transactional data (stock, sales, shifts, stock movements) is scoped per store via a store_id foreign key, while master data (items, categories, customers, suppliers) remains global and shared across all stores.

Store Context Mechanism

  • Terminals send an X-Store-Id HTTP header on every request identifying the active store.
  • StoreContextInterceptor reads the header, validates the authenticated user's access to that store, and sets a thread-local StoreContext for the duration of the request.
  • Store-scoped services call StoreContext.requireStoreId() to obtain the active store; this throws 400 Bad Request when no store has been selected.
  • The thread-local StoreContext is cleared after each request to prevent leakage across pooled request threads.

Store Access Enforcement

  • Store access is enforced on the backend, not merely hidden in the UI. If a user requests a store they are not assigned to (via X-Store-Id), StoreContextInterceptor returns 403 Forbidden.
  • Access is checked against the user_stores relationship via StoreRepository.userHasStoreAccess(userId, storeId).
  • The Super Administrator (user ID 1) bypasses the store-access check and has implicit access to all stores.

Landing Page Resolution

The LandingPageResolver infers a user's default landing page from their permission bitmask on login:

  • If USE_POS is present and VIEW_DASHBOARD is absent → landing page is POS.
  • Otherwise → landing page is DASHBOARD.

The resolved value is returned in the login response as landingPage, and the frontend routes the user accordingly after authentication.

API Response Format

All API responses use a standardized ApiResponse<T> wrapper:

{
  "success": true,
  "message": "Operation completed successfully",
  "data": { ... },
  "timestamp": "2026-08-14T13:30:00",

Data scoping: Master data (items, categories, customers, suppliers) is global/shared across all stores. Transactional data (stock, stock_transactions, sales, shifts) is scoped per store via a store_id foreign key. The stock table carries a composite unique constraint on (item_id, store_id) so each item has exactly one stock row per store. Because the stock table requires a store_id, creating an item now initializes a per-store stock row (quantity 0) for every store; previously item creation failed when no stock row could be created without a store.

6. Security

Authentication Flow

  1. User submits username and password to POST /api/auth/login
  2. Server validates credentials against bcrypt hash in database
  3. Server generates JWT access token (30 min) and refresh token (7 days)
  4. Client stores tokens (access in memory, refresh in httpOnly cookie or secure storage)
  5. Client includes access token in Authorization: Bearer header on subsequent requests
  6. When access token expires, client calls POST /api/auth/refresh with refresh token
  7. On logout, tokens are added to deny list and refresh token deleted from DB

Token Lifecycle

Token TypeExpiryStoragePurpose
Access Token30 minutesClient memory / localStorageAPI authentication
Refresh Token7 daysSecure storageObtain new access token

Token Deny List

On logout, the current access token's JTI (JWT ID) is added to an in-memory deny list. The deny list is checked on every request by the JWT authentication filter. Entries are auto-expired based on the token's original expiry time.

Permission Model

The system uses a bitwise permission model where each bit position (0–24) represents a specific permission. The permission bitmask is stored on the role (roles.access_rights), not on the individual user. A user is assigned exactly one role via users.role_id, and the user's effective permissions are derived authoritatively from that role — there are no per-user permission overrides. Bitwise AND operations provide fast permission checks.

Roles are dynamic and admin-managed at runtime through the /api/roles endpoints (gated by MANAGE_USERS). Because the permission bitmask is embedded in the JWT at login, changes to a role's permissions take effect on the affected user's next login or token refresh, not instantly.

Permission Check: @RequiresPermission

@RequiresPermission(Permission.MANAGE_ITEMS)
@PostMapping("/items")
public ApiResponse<ItemResponse> createItem(@RequestBody ItemRequest request) {
    // Only accessible if the user's role bitmask has the MANAGE_ITEMS bit set
}

Dynamic Roles

Roles are stored in the roles table and managed at runtime by administrators (no fixed enum). Each role holds its own permission bitmask in access_rights.

ColumnDescription

Reserved ADMIN role: Role id = 1 is seeded with access_rights = 33554431 (all 25 bits), is_system = 1. RoleServiceImpl rejects any attempt to update, deactivate, or delete it (returns 400). The UI also disables its edit/deactivate actions.

Guards

  • Backend (Controller): @RequiresPermission annotation checked by AOP aspect before method execution. Returns 403 if check fails.
  • Frontend (Router): Vue Router beforeEach guard checks user permissions from auth store against route meta.permission requirement. Redirects to unauthorized page if insufficient.

Store Access Enforcement

In addition to permission-based authorization, the system enforces per-store data isolation on the backend. Hiding stores in the UI is not sufficient — every store-scoped request is validated server-side.

  1. The terminal sends the active store as an X-Store-Id header (see API §5).
  2. StoreContextInterceptor resolves the authenticated user and calls StoreRepository.userHasStoreAccess(userId, storeId), which checks the user_stores relationship.
  3. If the user has access, the store ID is placed in a thread-local StoreContext. Store-scoped services read it via StoreContext.requireStoreId().
  4. If the user is not assigned to the requested store, the interceptor short-circuits with 403 Forbidden.
  5. If a store-scoped operation runs without any selected store, requireStoreId() raises 400 Bad Request.
Super Administrator bypass: User ID 1 (Super Administrator) bypasses the user_stores access check and has implicit access to all stores. All other users are restricted to their explicitly assigned stores.

Landing Page Resolution

On login, LandingPageResolver derives the user's default landing page from their permission bitmask, returned as landingPage in the login response:

ConditionResolved Landing Page
USE_POS present and VIEW_DASHBOARD absentPOS
OtherwiseDASHBOARD

This lets POS-only cashiers land directly on the POS screen while managers/admins land on the dashboard. The frontend routes accordingly after authentication.

12. Troubleshooting

Port 8080 Already in Use

Symptom: Tomcat fails to start with "Address already in use: bind"

Solution:

# Find the process using port 8080
# Windows:
netstat -ano | findstr :8080
taskkill /PID <pid> /F

# Linux:
lsof -i :8080
kill -9 <pid>

# Or change Tomcat port in server.xml

MySQL Connection Refused

Symptom: Communications link failure or Connection refused

Solutions:

  • Verify MySQL service is running: systemctl status mysql or check Windows Services
  • Confirm port matches configuration (default 3306, dev might use 3308)
  • Check application.yml datasource URL, username, and password
  • Verify MySQL user has GRANT on the database: SHOW GRANTS FOR 'inventory_user'@'localhost';
  • Check if MySQL is bound to localhost only (bind-address in my.cnf)

JWT Token Expired Errors (401)

Symptom: API returns 401 with "Token expired" after working previously

Solutions:

  • Access tokens expire after 30 minutes — client should auto-refresh using refresh token
  • If refresh token also expired (7 days), user must re-login
  • Check server clock synchronization (JWT validation is time-sensitive)
  • Verify the JWT secret hasn't changed between deployments (invalidates all tokens)

Permission Denied (403 Forbidden)

Symptom: User gets 403 error on certain actions

Solutions:

  • Check user's permission bitmask includes the required permission bit
  • Admin users should have permission value 33554431 (all 25 bits set)
  • Update permissions via Admin → Users → Edit User → Permissions
  • User must re-login after permission changes for new token to reflect updated permissions

Frontend Shows Blank Page

Symptom: White/blank page when accessing the application URL

Solutions:

  • Check browser console for JavaScript errors (F12 → Console)
  • Verify frontend was built: npm run build in frontend/
  • Confirm static files exist in src/main/resources/static/ after build
  • Check that the WAR was rebuilt after frontend changes: mvn clean package
  • Clear browser cache (Ctrl+Shift+R)
  • Verify context path matches (e.g., /inventory if deployed as inventory.war)

Reports Not Generating (Jasper Compilation Error)

Symptom: 500 error when generating reports, or "net.sf.jasperreports.engine.JRException"

Solutions:

  • Verify .jrxml files exist in src/main/resources/reports/
  • Check JasperReports dependency version in pom.xml
  • Ensure template was designed for JasperReports 7 (incompatible with older versions)
  • Check logs for specific compilation error — often a typo in field names or expressions
  • Test template independently in JasperSoft Studio before deployment

WAR Deployment Fails

Symptom: Application fails to start in Tomcat, 404 on all paths

Solutions:

  • Check TOMCAT_HOME/logs/catalina.out for startup errors
  • Verify Java version: Tomcat 9 supports up to Java 25 (check compatibility)
  • Ensure JAVA_HOME points to JDK 25
  • Check WAR file isn't corrupted: rebuild with mvn clean package
  • Verify no duplicate context paths in TOMCAT_HOME/conf/server.xml

Out of Memory on Tomcat

Symptom: java.lang.OutOfMemoryError: Java heap space

Solutions:

# Set memory in TOMCAT_HOME/bin/setenv.sh (Linux) or setenv.bat (Windows)
# Linux:
export JAVA_OPTS="-Xms512m -Xmx1024m -XX:+UseG1GC"

# Windows (setenv.bat):
set JAVA_OPTS=-Xms512m -Xmx1024m -XX:+UseG1GC
  • Monitor heap usage with jstat or VisualVM
  • Check for large report generations that load too many records — use pagination
  • Consider increasing to -Xmx2048m for production with heavy report usage
